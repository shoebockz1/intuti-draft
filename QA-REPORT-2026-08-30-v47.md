### 1. Acknowledged picks can be silently lost when the server restarts — HIGH

**Observed.** Six consecutive picks (round 3, slots 4–9) each returned `HTTP 200` with a full state body,
then vanished. State rolled back from R3.9 to R3.3. It recurred later in the run, losing one more
acknowledged pick (`cur` 83 → 82).

**Expected.** A pick confirmed to the client is durable.

**Cause.** `server/src/draft/store.ts:32` — `persistNow()` calls `void savePersistedState(...)`,
fire-and-forget. The route responds before the Redis write resolves, and `savePersistedState` swallows its
own errors (logs, never throws), so a failed write is invisible to the caller. On restart the server
hydrates from whatever snapshot did land. `persistNow()` is called at `store.ts` lines 144, 164, 189, 203,
215 and 230.

**Reproduction.** Make several picks in quick succession, restart the instance, re-read
`/api/draft/state`.

**Context and honesty about it.** Both occurrences coincided with Render 502s during a Cloudflare
rate-limit episode that **my own request rate provoked** — a real draft would not generate that load. The
race itself is independent of what triggers the restart, and Render's free tier does restart. Note the
transaction log is written through the same call, so it rolls back too and cannot be used to rebuild.

**Suggested fix.** Await the persist before acknowledging the pick, or return a write-sequence number the
client can verify. A persistence failure should probably surface to the commissioner rather than being
logged and dropped.

### 2. The 5th-place jump pick never appears on the draft board — MEDIUM

**Observed.** The finished board renders **180 cells for 181 picks**. The jump pick — Mark Jr, "Jared
Goff" — appears nowhere in the grid, and no `cell-jump` element is ever rendered, despite the legend
advertising a purple "5th jump" cell type.

**Expected.** The jump pick shows as its own distinctly-styled cell.

**Page/viewport.** `/` and `/boardonly`, all viewports.

**Cause.** `client/src/components/draft/Board.tsx` (~lines 45–65). The grid is one cell per
(round, owner), but the jump gives its owner **two** picks in one round — Mark Jr held R1.4 (jump) and
R1.7 (normal):

```js
const pick     = draft.picks.find(p => p.round===round && p.ownerIdx===owner.idx && !p.isFifthJump);
const jumpPick = draft.picks.find(p => p.round===round && p.ownerIdx===owner.idx &&  p.isFifthJump);
const disp = pick || jumpPick;   // normal pick always wins — jump is shadowed
```

Separately, the class chain tests `disp.type === "kept"` **before** `disp.type === "fifth-jump"`, so a
jump taken as a keep would render green even if it were shown. `.cell-jump`
(`client/src/styles/draft.css:141`) is therefore close to dead code.

**Mitigation.** Both `/` and `/boardonly` carry a separate 5th-place summary panel naming the pick
("Jared Goff — Mark Jr · After Round 1, Pick 4"), so the information is not lost — only absent from the
board itself.

**Note.** Fixing this needs a layout decision, since the grid assumes one pick per owner per round.

### 3. Rejected picks are written into the transaction log — MEDIUM-LOW

**Observed.** 5 of 188 log entries record actions that never happened:

- 2 × `action:"keep", ownerName:"Tee"` with **no** `playerName` — the broken-seal rejections from check 6.
- 3 × `keep`/`unprotected` with **neither** owner nor player — pick attempts made after the draft was
  already complete.

**Expected.** The log records only picks that were actually recorded.

**Impact.** The transaction log is the audit trail used to reconstruct a draft, so phantom entries
undermine exactly the job it exists for.

### 4. On the jump pick, the "Own player" tab misstates the cost of drafting unprotected — LOW

**Observed.** With Mark Jr on the clock for the jump, the default "Own player" tab reads
*"Use Keep buttons below, or switch to Unprotected to **break seal**."* Switching to the Unprotected tab
correctly reads *"5th place jump — seal stays intact after this pick."*

**Expected.** On the jump pick, drafting unprotected does **not** break the seal.

**Why it matters.** This sits on exactly the path the brief flags as dangerous: the panel defaults to
"Own player", so Keep is the most natural action — and the text actively discourages the alternative by
misdescribing it. The underlying behaviour is correct; only the wording is wrong.

---

### 5. Rejected picks return HTTP 200 — LOW

**Observed.** A keep from a broken-seal owner returns `200` with a full state body plus a `toast`
explaining the refusal. A pick attempted after the draft is complete also returns `200`, with no toast at
all.

**Expected.** A refusal is distinguishable from success without inspecting the body.

**Note.** Behaviourally safe — nothing was recorded and the clock never advanced in either case, so
check 6 passes. Flagged only because clients cannot tell success from refusal by status, and the
post-completion case carries no message. Changing status codes may break the client's `200 + toast`
expectation, so confirm before altering.

## Could not verify, and why

- **An owner running out of protected players.** Structurally unreachable with the 2025 fixture — every
  owner holds 19–20 protected players against 18 rounds, so an intact seal can never exhaust its list.
  Needs a purpose-built draft with short rosters.
- **An owner with zero protected players**, and **very long names** in nav, on-clock bar and board
  headers. Both need custom setup, which would have meant discarding the completed rehearsal.
- **The "no draft in progress" state** of `/boardonly` and `/rosters`. The window between wiping and
  starting passed before it was captured; re-testing needs another wipe.
- **Undo of a keep and of a plain unprotected pick** specifically, and **reset / restore** log entries and
  snapshot restore. These need commissioner auth, lost to a restart (finding 8). Undo itself is proven
  correct on the hardest case — the jump pick.
- **Setup interactions**: ↑/↓ reordering swapping a name together with its protected players,
  Sleeper-backed search, "Clear all", and the confirmation on re-clicking "Start draft" mid-draft. Same
  auth blocker, and several would have destroyed the finished draft.
- **Live multi-viewer propagation** within ~2s across two devices. The draft completed before a clean
  two-window test. Partial evidence: throughout the run the UI correctly reflected picks driven through
  the API, so polling does propagate.
- **Undo disabled at `historyDepth: 0`.** Confirmed by binding —
  `undoDisabled = (draft.historyDepth ?? draft.history.length) === 0` (`DraftScreen.tsx:20`) — and by
  observing it enable and track correctly, but not observed in the disabled state, which only exists
  before the first pick.

A short second draft with hand-made short rosters would close the first two items and most of the setup
sweep in roughly fifteen minutes.
